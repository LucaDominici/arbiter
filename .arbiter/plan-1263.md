# Plan — #1263 ship `--batch` native overnight multi-issue mode

## Goal

Port `/auto --batch` as a native `arbiter ship` capability: process N issues
unattended, ONE fresh sub-agent per issue (clean context), per-issue STOP
isolation, writing a date-stamped `batch-report-<date>.json`. This is the
wave-orchestrator pattern (`.claude/prompts/opus-4.8-harness-wave-orchestrator.md`)
as a first-class feature instead of a prompt.

Scope FROZEN to #1263. Do NOT build #1267 (dispatch matrix) or #1258 (autonomy
levels) — leave documented tie-in comments only.

## Design (mirror src/affinity + src/sizing pure-core + adapter split)

1. **Pure batch core** `src/batch/batch.ts`:
   - `runBatch(issueIds, { runIssue, date })` — pure, no I/O, never spawns.
   - `runIssue: (id: string) => IssueOutcome` is the injectable seam (tests stub;
     adapter injects the real ship-driver). `date` injected so the core is
     deterministic.
   - **Per-issue STOP isolation (the crux):** each iteration is wrapped in
     try/catch. A throw/blocker on issue k of N records a `blocked` outcome with
     the blocker message and the loop CONTINUES — mirroring how sizing/affinity
     "never throw, degrade". This is the analog of fail-closed isolation.
   - Aggregates `BatchReport`: per-issue `{ issueId, outcome, branch?, sha?, blocker? }`
     + top-level `{ date, total, succeeded, blocked, issues }`.
   - `formatBatchLines(report)` — human-readable summary lines (header always present).

2. **Adapter** `src/batch/batch-runner.ts` (I/O lives here):
   - `parseIssueList(raw)` — comma-separated → validated positive-int `#`-prefixed ids.
   - `batchReportPath(date)` → `batch-report-<date>.json`.
   - `writeBatchReport(dir, report)` — the file write (I/O).
   - `runShipBatch(issueIds, { dir, runIssue })` — generates the date, calls the
     pure `runBatch`, writes the report, returns lines. `runIssue` defaults to a
     documented real-runner seam.
   - **Clean-context contract:** the default `runIssue` is the documented
     integration point — each call models a FRESH sub-agent per issue (clean
     context). The harness/orchestrator supplies the live LLM spawn; arbiter owns
     the loop + report + isolation. Comment marks this seam. `// #1258 autonomy-levels tie-in:` one-liner at the natural hook.

3. **CLI wiring** `src/cli.ts` (EXISTING file — no new src/commands file, sidesteps CANON-06 new-file):
   - Add `--batch <issues>` option to the existing `ship` command (parser mirrors
     `--units`: positive ints, comma-separated). If `opts.batch` present → batch
     path; else the existing single-id path is UNTOUCHED (regression discipline,
     #1260 RT-05).

4. **Docs (dual-sided):** `--batch` is a new flag → regenerate the generated CLI
   region with `node scripts/gen-cli-ref.mjs` so INV-111 cli-ref parity stays
   green. This is a docs change → commit must NOT use `[skip-docs]`.

## Central test

A stubbed runner that succeeds on #A, THROWS on #B, succeeds on #C → report has
#A green, #B blocked-with-reason, #C green, and the loop completed all three.
The red test MUST cover mid-batch failure or it does not test the feature.

## Existing Code Survey

**Target:** `src/batch/batch.ts`, `src/batch/batch-runner.ts`

**Decision:** create (new files justified — distinct responsibility)

| Grepped for | Found | Reuse / reject |
| --- | --- | --- |
| `runTaskShip`, `shipStepFor` in `src/commands/task-ship.ts` | single-issue ship orchestrator (computes next step for ONE issue, advances one phase) | REUSE conceptually as the per-issue runner the adapter wraps; do NOT extend it — it is single-issue by contract and adding a multi-issue loop would pollute it |
| `scoreAffinity`, `renderShipAffinity`, `fetchAffinityContext` in `src/affinity/` | pure scorer + `gh` adapter + injectable fetcher seam; never-throws degradation | REUSE the PATTERN (pure-core + adapter + injectable seam + never-throw degradation); not the code (affinity scores issues, does not orchestrate a run loop) |
| `computeShipSize`, `sizeVerticals` in `src/sizing/` | pure size scorer + adapter split, fail-safe degradation | REUSE the structural pattern (pure module + adapter, `DEFAULT` fail-safe direction); not the code |
| `runCliJson` in `src/utils/run-cli.js`, `parseInt` `--units` parser in `src/cli.ts` | shared shell-out helper (INV-12) + positive-int flag parser | REUSE both verbatim where I/O / parsing is needed |
| `batch` across `src/` (`grep -rln batch src/`) | wizard/prompts, anti-drift-validators, claude generator, configure — all unrelated to ship batch orchestration | no batch ORCHESTRATION loop exists; nothing to refactor into |

**Rationale (≥200 chars):** No existing module orchestrates a multi-issue run
loop with per-issue STOP isolation and report aggregation. `task-ship.ts` is
single-issue by explicit contract (its header states "ships ONE issue"); folding
a batch loop into it would entangle single-issue next-step computation with
multi-issue iteration, violating its single responsibility and the affinity/
sizing precedent that keeps each ship concern in its own module. The affinity
(#1259) and sizing (#1260) lanes deliberately established a per-concern
`src/<concern>/` directory with a pure core plus a thin adapter and an injectable
seam; the batch concern is the natural next member of that family. Reusing the
PATTERN (pure + adapter + injectable runner + never-throw degradation) while
creating a new `src/batch/` directory keeps the abstraction clean, makes the loop
unit-testable with a stubbed runner (no live LLM), and isolates the file-write
I/O from the deterministic core. A new directory is therefore justified by a
distinct responsibility (multi-issue orchestration), not lower creation friction.
