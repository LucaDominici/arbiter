# Plan: Issue #2501 — cross-model-review E2E test wall-clock determinism

## Acceptance Criteria

- [ ] AC-1: Assert on the dispatch contract deterministically instead of on a real
      timeout — an injected clock, or a stub seat that resolves immediately — so a
      slow host produces a slow test, never a red one.
- [ ] AC-2: If the degrade-on-timeout behaviour genuinely needs coverage, keep a
      separate, explicitly-named test for it with the timeout injected rather than
      waited out. Do not delete coverage to make the flake go away.
- [ ] AC-3: Do NOT skip, disable, `.skip`, `.todo` or quarantine the test.
- [ ] AC-4: Do NOT simply raise the timeouts as the sole fix — remove the wall-clock
      dependency, not widen it.
- [ ] AC-5: Do NOT weaken the assertion (e.g. `toHaveLength(1)` → `toBeGreaterThanOrEqual(0)`).
      The test must still prove the seat was invoked and fulfilled.
- [ ] AC-6: Reproduce the flake first if possible (run under artificial CPU load and
      show it red on the unfixed tree); if it cannot be reproduced, say so plainly.
- [ ] AC-7: After the fix, run the same test repeatedly under load (5+ consecutive
      runs) and show it green every time.
- [ ] AC-8: Confirm the assertion still fails when the contract is genuinely broken
      — break the dispatch wiring deliberately, show the test red, then restore.

## Non-Goals

- Not changing the `crossModelReview` production feature/behavior itself — only the
  test fixture's timing assumptions and the addition of a deterministic timeout test.
- Not addressing unrelated flakiness elsewhere in the suite (out of scope for #2501;
  any such finding is captured via `arbiter note`, not fixed inline).
- Not adding a fake-clock/time-mocking library — the seat under test is a real,
  separate OS subprocess spawned by a real `dist/cli.js`, which a test-process-local
  fake timer cannot reach; determinism instead comes from removing the tight ceiling
  and by using a fixed one-directional inequality (short timeout vs. long sleep) for
  the dedicated timeout test.

## Scope

`__tests__/commands/cross-model-review.test.ts` > "arbiter ship cross-model
wiring > invokes the external seat from the real CLI refactor boundary" races
a real subprocess (a stub `codex` binary invoked through a real
`dist/cli.js ship` spawn) against an artificially tight
`crossModelReview.timeoutMs: 5_000` fixture value. Under host contention the
trivial stub script does not get scheduled/reaped inside 5s, `invokeCodex`'s
`runCli` kills it as a timeout, and the dispatch degrades to
`fulfilled: []` — a false red on a correctly-wired system, purely a function
of host speed.

Fix: remove the tight, test-picked ceiling (replace with the documented
production default, `DEFAULT_CROSS_MODEL_REVIEW.timeoutMs` = `300_000`, already
used by the `cfg` fixture at the top of the same file for the mocked-unit
tests) so the happy-path assertion no longer races host scheduling — a slow
host produces a slow test, never a red one. The stub seat itself still
resolves near-instantly; the ceiling is a backstop, not a wait. Also widen the
two outer `spawnSync(..., {timeout: 30_000})` calls to `60_000` (matching the
`ship` E2E convention in `ship-tier.test.ts`) since the issue names the outer
bound as a second nested wall-clock dependency sharing an order of magnitude
with the old inner value.

Separately, the degrade-on-timeout path was previously exercised only
incidentally (by the same race, when it went wrong) and had no deterministic,
intentional coverage of its own. Add one to the existing real-runCli-boundary
file `__tests__/integrations/external-review-subprocess.test.ts` (already
built for exactly this: a real `codex` PATH stub, no `dist/cli.js` spawn) —
a stub that `sleep 5`s against a `timeoutMs: 200` ceiling, which is a fixed,
one-directional inequality (200ms always elapses long before a 5s sleep could
possibly finish) rather than a race, so it is deterministic on any host.

## Existing Code Survey

**Target:** test-only change; no new `src/` file. CANON-16 does not hard-apply
(no file under `src/`, `src/generators/`, `src/templates/`, `src/commands/` is
being created), but the refactor-first spirit still applies to the two test
files touched.

- `grep -n "timeoutMs" __tests__/commands/cross-model-review.test.ts` → the
  `cfg` fixture already at the top of the file (mocked-`invokeExternalReview`
  unit tests) uses `timeoutMs: 300_000` — the E2E fixture's `5_000` was the
  only outlier, confirming `300_000` is the file's own existing convention,
  not a fix-invented number.
- `grep -n "DEFAULT_CROSS_MODEL_REVIEW" src/config/schema.ts` → `timeoutMs: 300_000`
  is the documented production default; the fix restores it rather than
  picking an arbitrary bigger number.
- `find __tests__ -iname "*external-review*"` → two files:
  `external-review.test.ts` (mocked `runCli`, already covers a
  *probe*-timeout via `access.error`) and
  `external-review-subprocess.test.ts` ("exercise the real runCli boundary
  with a PATH stub" — exactly the right altitude for a real,
  deterministic-by-construction subprocess timeout test). Extended the
  latter with one new `it(...)` rather than creating a third file.
- `grep -rn "dist/cli.js" __tests__ | xargs grep -n "timeout:"` → `ship`-command
  E2E tests elsewhere in the suite use `60_000`/`120_000` for the outer
  `spawnSync` backstop (e.g. `ship-tier.test.ts`); `30_000` was the outlier
  shared with the too-tight inner value.

**Decision:** extend both existing files; no new test file created.

## Verification Plan

1. Reproduce the reported failure deterministically (ambient CPU-load
   injection did not budge this sandbox's subprocess timing — documented as a
   plain limitation) by temporarily making the stub `codex` `sleep 6` against
   the **unmodified** `timeoutMs: 5_000`: reproduces the exact reported
   assertion (`expected [] to have a length of 1 but got +0`).
2. Apply the fix (300_000 / 60_000).
3. Re-apply the identical `sleep 6` injection against the **fixed** tree: the
   test now passes, slower (~7s) instead of red — proves the wall-clock
   dependency was removed, not merely widened past the specific case observed.
4. Run the fixed test 5+ consecutive times while a background CPU-load
   generator saturates the host — green every time.
5. Deliberately break `fulfilledEntries` in
   `src/integrations/external-review.ts` (return `[]` unconditionally) to
   simulate a genuinely broken dispatch contract; confirm the test goes red
   with the same assertion; revert.
6. Run the new deterministic timeout test in isolation — confirm it completes
   in ~200ms (bounded by the injected timeout, not the 5s sleep), proving it
   is event-driven and not itself a wait.
