# #2919(a) — `gateLockPathFor` ignores inherited `GIT_DIR`/`GIT_WORK_TREE`

## Acceptance Criteria

Issue criteria, quoted verbatim (part (b); they stay open on #2919 — this PR says `Refs #2919`):

- AC-2919.1: The test is deterministic under CI load. Its git setup uses bounded, minimal work (for example a single shared fixture repo), or it has a per-test timeout justified by a measured p99. It never depends on the 30 s default under contention.
- AC-2919.2: 20 consecutive runs of the file under `--pool=forks` on a loaded runner show no timeout. Record the measurement in the PR.

Part (a), delivered here:

- AC-2919.3: `gateLockPathFor(dir)` resolves the lock path of `dir`'s own repository even when the process inherits `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE` pointing at another repository; a regression test proves it (non-vacuous: two repos resolve to distinct locks first).

- `src/commands/gate-exec.ts` `deriveGateKey` has the same hole: follow-up issue, not fixed here.
- Any `src/` edit, new export, CLI option or `E_` code.
