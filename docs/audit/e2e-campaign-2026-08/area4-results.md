## Findings (root cause · severity · fix proposal)

### F1 — `gate-exec`: the mutex is released only when the LAST descendant dies, not when the gate ends — **HIGH**

**Observable.** `flock(1)` opens the lock file on fd 3 and that fd is inherited by every descendant of the gated command. Measured fd census while a gate was held:

```
pid=895923 holds fd 3 -> /run/user/1000/arbiter/98ebd6cf381c4f14-gate.lock (flock)
pid=895924 holds fd 3 -> …-gate.lock (sh)
pid=895925 holds fd 3 -> …-gate.lock (sleep)
```

Three consequences, all reproduced:

| kill target                           | node | flock     | child     | lock after                                     | waiter                         |
| ------------------------------------- | ---- | --------- | --------- | ---------------------------------------------- | ------------------------------ |
| `arbiter` (node) pid                  | dead | **alive** | **alive** | **HELD**                                       | timed out (exit 124) after 18s |
| `flock` pid                           | dead | dead      | **alive** | **HELD**                                       | timed out (exit 124) after 18s |
| direct child (`sh`)                   | dead | dead      | dead      | **HELD** (grandchild `sleep` still holds fd 3) | timed out (exit 124)           |
| whole process group (`kill -9 -PGID`) | dead | dead      | dead      | FREE                                           | ran in **0.007s**              |

Worst case — no kill needed at all:

```
$ node dist/cli.js gate-exec -- sh -c 'nohup sleep 20 >/dev/null 2>&1 & echo GATE-DONE; exit 0'
GATE-DONE
gate1 exit=0 elapsed=.45s
probe after gate1 returned: HELD
  LEAKED HOLDER pid=1029996 cmd=sleep 20
gate2 exit=0 blocked_for=17.94s
```

**Root cause.** `gateExecArgv` (`src/commands/gate-exec.ts`) emits `['flock','--',lockPath,...cmdArgs]` with **no `-o/--close`**, so the lock fd is passed through to the gated command and every process it spawns. Separately, `runGateExec` runs flock via `runInteractive` as a child of the node process, so killing `arbiter` orphans (rather than terminates) the gate. The module docstring's claim — "the release is guaranteed on fd death — including SIGKILL/OOM-kill of the holder … No 1h stale-lock stall" — is true only for the fd, and the fd is not co-terminous with either the `arbiter` process or the gate.

**Why HIGH.** Real gates spawn daemons (vitest/jest workers, the esbuild service, `npm run dev &`, docker-compose shells). Any such gate holds the repo-wide mutex for the daemon's lifetime, not the gate's; a daemon that never exits deadlocks **every worktree of the repo** indefinitely. There is no recovery path — `arbiter doctor recover-lock` does not know about this lock (it only manages `.arbiter/.lock`/`kit.lock`), `flock` writes nothing to the file, so the operator has no way to find the holder short of a manual `/proc/*/fd` scan.

**Fix proposal.**

1. **One flag, fixes the leak and kill-scenarios B/D:** add `-o` to `gateExecArgv` → `['flock','-o','--',lockPath,...cmdArgs]`. Verified live without touching arbiter:
   `flock -o -- $LOCK sh -c 'nohup sleep 20 >/dev/null 2>&1 & echo gated-done'` → `with -o after gate returns: FREE`.
   Caveat to document: with `-o` the lock is released the moment the command _starts_, so it serializes the gate's start, not its whole run.
   **CORRECTION (#2330):** this caveat is wrong. `flock(1)` closes the descriptor in the child only; the parent retains it for the wrapped command's whole run (re-measured 2026-08-23). What `-o` really changes is that killing `flock` alone now frees the mutex while the gate keeps running — see ADR-103 §2 and its Consequences. If the mutex must cover the whole run, the alternative is to keep the fd only in flock and `setsid`/`close-on-exec` the payload.
2. **Scenario A needs a separate fix:** `runGateExec` should install `SIGTERM`/`SIGINT`/exit handlers that kill the flock child's _process group_, and the child should be spawned with `detached:false` + an explicit group kill, so that killing `arbiter` terminates the gate instead of orphaning it. (`-o` does not help here — the orphaned flock still holds the fd.)
3. **Operator escape hatch:** teach `arbiter doctor` about the gate mutex — report the lock path, whether it is held (`flock -n <path> true`), and which pids hold fd on it; offer a `--repair` that kills the holder group. Today `doctor` is blind to it.

### F2 — `doctor recover-lock` cannot remove the corrupt lock that `doctor` itself tells you to remove — **MEDIUM**

```
$ printf 'not json at all' > .arbiter/.lock
$ node dist/cli.js doctor
  [WARN]  .arbiter/.lock unreadable  — lock file exists but contents are not valid JSON
         hint: Run `arbiter doctor recover-lock` to remove it.
$ node dist/cli.js doctor recover-lock
  No lock file found in /tmp/rtm-a4-Mt7k/.arbiter
$ node dist/cli.js configure --set governanceLevel=L1 ; echo $?
  Error: Lock already exists at /tmp/rtm-a4-Mt7k/.arbiter/.lock.
1
```

**Root cause.** `runDoctorRecoverLock` (`src/commands/doctor/recover-lock.ts:37-40`) does `const info = await inspectLock(lockPath); if (!info) continue` — and `readLockInfo` (`src/utils/file-lock.ts:111-129`) returns `null` for any content that is not parseable JSON with all six fields. The unlink is inside the `info`-truthy branch, so it is unreachable for exactly the case the health check points at. Every lock-taking command then dies with `E_LOCK_CONFLICT` (`acquireLock` retries 3× and rethrows, `file-lock.ts:242-275`).

**Severity MEDIUM** — the repo is stuck for every arbiter command that writes config until a human runs `rm .arbiter/.lock`, but the escape is trivial once known and no data is lost.

**Fix.** In `runDoctorRecoverLock`, when `inspectLock` returns nothing but the file exists, unlink it (that is the "unreadable" case health already classifies) and report it as `released: true, info: undefined`. One `existsSync` + `unlinkSync` branch.

### F3 — anti-fake-green aggregate FAILS: deleting one `existsSync`-gated config silently removes a whole L1 lane and the gate stays green — **HIGH**

This is the mandated "break one guard and prove the aggregate reds" test **in the target**, and the aggregate did **not** red.

```
$ mv eslint.config.static.mjs /tmp/…
$ node scripts/check-all.mjs L1
[CHECK] static analysis ... SKIP (run: arbiter update)
…
=== ALL PASSED ===
gate exit=0
static-analysis lines in the summary table: 0
warnings naming the missing file: 0
unwired guards: PASS
.arbiter/gate-pass.json: still stamped {"level":"L1"} green
```

**Root cause.** Generated `scripts/check-all.mjs:194-198`:

```js
if (existsSync('eslint.config.static.mjs')) {
  runCheck('static analysis', 'npx', ['eslint','--config','eslint.config.static.mjs', …]);
} else {
  console.log('[CHECK] static analysis ... SKIP (run: arbiter update)');
}
```

The guard exists so the check degrades gracefully in projects where the config was never emitted — but at runtime "never emitted" and "deleted/renamed after emission" are indistinguishable, so removing one file removes a wired L1 lane with no red, no summary row, and a green `gate-pass.json`. **Control:** deleting the *un*guarded `eslint.config.mjs` correctly reds (`lint FAIL 207ms`, exit 1), which is the desired behaviour. The same pattern is at `:204` (`eslint.config.no-fake-db.mjs`, INV-34), `:468` (`check-iso9001.mjs`) and `:472` (`check-regulated-overlay.mjs`).

**Severity HIGH** — it is a one-file, no-trace way to disable a governance lane and still ship a green gate marker that `enforce-gate-before-pr` and the pre-push hook will accept. `doctor fail-open-census` does **not** flag it (it censuses `command -v X || …` shell presence-gates, and reported "no fail-open patterns found").

**Fix proposal.** Make emission-time expectations explicit rather than inferred at runtime: have `arbiter init/update` record the set of emitted optional configs in `.arbiter/.arbiter-generated.json` (already the generation snapshot), and change the `else` branch to `if (wasEmitted('eslint.config.static.mjs')) FAIL else SKIP`. Cheaper interim: make the `else` branch a hard FAIL whenever `arbiter.json` declares the corresponding capability, and extend `doctor fail-open-census` to census `existsSync(...) { runCheck } else { console.log(… SKIP …) }` in generated gates — the JS twin of the shell pattern it already censuses.

### F4 — `doctor --prove-gates` proves arbiter's own probes, never the target's 50 wired checks — **MEDIUM (coverage scope)**

`--prove-gates` runs 12 registered `GateProof`s (`src/conformance/gate-proofs.ts`); each `seed(dir)` writes a negative fixture into a **fresh temp dir** and `run(dir)` calls an in-process probe from `src/conformance/dimensions.ts`. It never executes a target script. Measured in the governed target: 11/12 bite, 1 is `NV` (`D-INVARIANTS-ENFORCED — no invariants catalog found`), exit 1. Meanwhile the target's own gate wires **45 checks at L1 / 50 at L2**, and none of them has a negative proof:

```
$ printf '#!/usr/bin/env node\nprocess.exit(0)\n' > scripts/check-doc-links.mjs   # neuter a wired L1 gate
$ node dist/cli.js doctor --prove-gates --json | …   → notBiting=1 biting=11   (unchanged)
$ node scripts/check-all.mjs L1                      → === ALL PASSED === exit 0
```

**Severity MEDIUM** — no false green today (the proofs do what they claim for the 12 dimensions), but the command reads as "every wired gate bites" and it is not that. Combined with F3, a governed project has no mechanism that would notice a neutered or silently-skipped check.

**Fix proposal.** Either (a) rename/scope the output so it says "12 conformance dimensions", not "tier-1 gates", and stop implying wired-check coverage; or (b) add a target-side mode — for each `runCheck(name, cmd, args)` in the generated `check-all.mjs`, run the check against a seeded negative fixture and assert non-zero. The generated gate already has the `--gate <name>` single-check runner (#2078), which is most of the machinery.
