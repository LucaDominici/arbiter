# ADR-025 — Claim-Verified Governance Documents

**Status:** Accepted
**Date:** 2026-04-16
**Issue:** #90 (MI — STRIDE Skeleton Enforcement)

---

## Context

Governance documents such as threat models and responsibility matrices make
factual claims about security properties and process ownership. Without
traceability, these claims are assertions — they cannot be mechanically
verified, tend to drift from the actual codebase, and provide false assurance
in audits.

Arbiter already enforces code-level gates (lint, coverage, mutation). The
same philosophy — _gate failures, not warnings_ — must extend to governance
documents whenever those documents make HIGH or CRITICAL claims.

---

## Decision

Governance documents generated by arbiter follow the **claim-verified** pattern:

1. **Empty skeleton by default.** Templates generate schema-only tables with
   no pre-populated entries. An empty skeleton always passes the gate.

2. **Tag-based verification for HIGH/CRITICAL claims.** When a practitioner
   adds a HIGH or CRITICAL row to a governance document, they must annotate
   the corresponding test with a structured comment:
   - STRIDE threats: `// @Security:<threat-id>`
   - RACI responsibilities: `// @RACI:<responsibility-id>`

3. **Gate failure on missing evidence.** `scripts/check-stride-traceability.mjs`
   (generated by arbiter) scans HIGH/CRITICAL rows and verifies each has a
   matching annotation in the codebase. Missing evidence → exit 1 with a
   file-and-line reference to the unverified claim.

4. **Gate invocation at L2.** The traceability check runs inside the
   `if (level === 'L2')` block of the generated `check-all.mjs`, making it
   mandatory for pre-push gates and CI.

5. **User-owned documents, arbiter-owned scripts.** STRIDE.md and RACI.md use
   `skipIfExists: true` (never overwritten on `arbiter update`). The checker
   script uses `skipIfExists: false` (always regenerated to pick up gate logic
   improvements).

---

## Documents in scope

| Document            | Path                      | Tag prefix     | Enforced column   |
| ------------------- | ------------------------- | -------------- | ----------------- |
| STRIDE threat model | `docs/SECURITY/STRIDE.md` | `@Security`    | Severity (col 4)  |
| RACI matrix         | `docs/GOVERNANCE/RACI.md` | `@RACI`        | Priority (col 7)  |
| RTM (opt-in)        | `docs/GOVERNANCE/RTM.md`  | `@Requirement` | Priority (future) |

---

## Consequences

**Positive:**

- HIGH/CRITICAL governance claims become mechanically verifiable.
- Audit evidence is co-located with the test that provides it.
- Empty skeleton passes gate immediately — no friction for new projects.
- Drift is impossible: renaming a threat ID without updating the test fails CI.

**Negative:**

- Teams must annotate tests when adding HIGH/CRITICAL threats. This is
  intentional friction — unverified HIGH/CRITICAL claims are worse than
  acknowledged gaps.
- The file-walk approach in the checker is O(n) in project file count. On
  very large monorepos (>100k files) this may be slow; teams can narrow the
  scan scope by customising the generated script's `SCAN_EXTS`/`EXCLUDE_DIRS`.

---

## Alternatives considered

- **Link column in the table**: Require a URL or path reference in the table
  itself. Rejected — links rot, and the checker cannot verify that a URL
  points to an actual test.
- **Separate evidence registry**: A JSON file mapping threat IDs to test paths.
  Rejected — double maintenance burden; annotations are DRY by definition.
- **Warn-only mode**: Report missing evidence as warnings, not failures.
  Rejected — warnings are ignored; gate failures are not.
