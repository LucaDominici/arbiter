## Decision Tree — Rollback vs Fix-Forward

Before executing a rollback, use this decision tree:

```
Is the issue data corruption?
├── YES → Rollback immediately. Data integrity > availability.
└── NO →
    Is the bug causing complete service unavailability?
    ├── YES →
    │   Can the previous revision handle current load?
    │   ├── YES → Container revision rollback (§2). DB rollback only if schema broke.
    │   └── NO  → Fix-forward + scale up. Rollback would just move the problem.
    └── NO (degraded but functional) →
        Is a fix deployable within 30 minutes?
        ├── YES → Fix-forward. Deploy hotfix PR.
        └── NO  → Rollback (§2). DB schema rollback rarely needed for logic bugs.
```

**Rule of thumb**: rollback is fast and reversible — prefer it when uncertain.
DB schema rollback is irreversible for data; plan carefully.

## § 2 — Container Revision Rollback

### Step 1: Identify the target revision

```bash
# List recent deployments / revisions
# (substitute with your platform's equivalent)
# Example: Azure Container Apps
az containerapp revision list --name <app-name> --resource-group <rg> \
  --query "[].{name:name,active:properties.active,createdAt:systemData.createdAt}" \
  --output table

# Example: Kubernetes
kubectl rollout history deployment/<deployment-name>
```

### Step 2: Activate the target revision

```bash
# Azure Container Apps — activate a specific revision
az containerapp revision activate --name <app-name> --resource-group <rg> \
  --revision <revision-name>

# Then deactivate the bad revision
az containerapp revision deactivate --name <app-name> --resource-group <rg> \
  --revision <bad-revision-name>

# Kubernetes — rollback to previous
kubectl rollout undo deployment/<deployment-name>

# Kubernetes — rollback to specific revision
kubectl rollout undo deployment/<deployment-name> --to-revision=<N>
```

## § 3 — Database Schema Rollback

> **WARNING**: Schema rollbacks can destroy data. Proceed only when data corruption is confirmed or a schema change caused the outage.

- [ ] Identify the migration that introduced the issue
- [ ] Confirm a rollback migration exists or can be safely crafted
- [ ] Back up the current database before any DDL change
- [ ] Apply the rollback migration in the migration tool

```bash
# Example: Flyway
./mvnw flyway:undo

# Example: Liquibase
liquibase rollbackCount 1

# Example: alembic (Python)
alembic downgrade -1
```

## § 4 — Post-Rollback Checklist

- [ ] Liveness and readiness probes GREEN
- [ ] Error rate returned to baseline (check dashboards)
- [ ] Alert channel updated with rollback status
- [ ] Incident ticket opened (include: timeline, cause hypothesis, rollback steps taken)
- [ ] Follow-up PR opened to fix the root cause and re-deploy

## § 5 — Anti-Patterns

| Anti-Pattern                            | Why It Fails                        |
| --------------------------------------- | ----------------------------------- |
| Rolling back DB schema without backup   | Irreversible data loss              |
| Partial rollback (app only, not config) | Config drift causes silent failures |
| Rolling back without checking traffic   | Rollback may not reduce load spike  |
| Skipping post-rollback health check     | Leaves team in uncertainty          |
