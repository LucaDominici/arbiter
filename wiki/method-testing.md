## Mock Policy

### What CAN be mocked

- External third-party APIs (payment, email, SMS, maps, weather)
- External authentication providers when running unit tests
- Outbound HTTP to services outside the system boundary

### What CANNOT be mocked

- Core domain logic — test the real implementation
- Internal application services — inject real or in-memory fakes, not mocks
- Auth layer — test with a real user context or test token

**Rule:** if you are mocking to make a test easier to write, ask whether the design needs to change instead.

---

## E2E Policy

- Core API endpoints (`/api/*` or equivalent) must be tested against the **real running service**
- Mocking core API responses in E2E tests is **prohibited** — it tests the mock, not the system
- External providers (payment, email) MAY be stubbed via WireMock or equivalent
- Minimum smoke test set (mandatory before each release):
  1. Authentication flow (login / token refresh)
  2. Core CRUD operation
  3. Authorization enforcement (role or permission check)

## Mandatory Test Patterns

Every feature implementation must include tests for each of the following patterns:

| Pattern             | Description                                                        | Required |
| ------------------- | ------------------------------------------------------------------ | -------- |
| Happy path          | The primary success case with valid inputs                         | ✓        |
| Null / empty input  | Behavior when required inputs are absent or empty                  | ✓        |
| Not found           | Resource lookup when the target does not exist                     | ✓        |
| Business rule       | Domain invariant violations (invalid state transitions, etc.)      | ✓        |
| Auth / unauthorized | Access attempt without valid credentials or insufficient privilege | ✓        |
| Tenant isolation    | Data from tenant A must not leak to tenant B                       | ✓        |
| Concurrency         | Concurrent access does not produce incorrect results               | ✓        |

| Level                 | Description                                                           | Tools        |
| --------------------- | --------------------------------------------------------------------- | ------------ |

| **L2 Property-Based** | Generative / property-based tests to find edge cases                  | `fast-check` |

---

## Conventions

- **L1 tests** run on every commit (pre-commit hook via `scripts/check-all.mjs L1`).
- **L2+ tests** run on push/PR (`scripts/check-all.mjs L2`).
- Test files live next to the code they test (co-located) or in a top-level `__tests__/` directory.
- Every public function/method must have at least one test.
- Property-based tests must cover all public API inputs. Use `fast-check`.

## Test Type Codes

| Code    | Name                | Description                                                                         |
| ------- | ------------------- | ----------------------------------------------------------------------------------- |
| **UT**  | Unit Test           | Pure function / class isolation — no I/O, no DB (INV-26)                            |
| **IT**  | Integration Test    | Two or more real collaborators (DB, queue, cache) — Testcontainers where applicable |
| **AU**  | API / Contract Unit | HTTP boundary — input validation, error contracts, OpenAPI parity (INV-47)          |
| **ST**  | System / E2E Test   | Full stack — real infra, real browser (Playwright) where applicable                 |
