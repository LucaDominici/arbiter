# Security Policy

## Reporting a Vulnerability

**Do not open a public GitHub issue for security vulnerabilities.**

Use one of the following private channels:

### Option 1 — GitHub Private Vulnerability Reporting (preferred)

Once the repository is public, use GitHub's native private reporting:

1. Go to the **Security** tab of the repository
2. Click **"Report a vulnerability"**
3. Fill in the vulnerability report form
4. Submit — this creates a private advisory visible only to maintainers

This is the preferred channel as it keeps the disclosure entirely within GitHub and
enables coordinated patch and advisory publication.

> **Note:** Private vulnerability reporting is available on public GitHub repositories.
> Until the repository is public, use the email channel below.

### Option 2 — Email

Send a report to: **ulfwerenar@gmail.com**

Please include:

- Description of the vulnerability
- Steps to reproduce
- Affected versions
- Potential impact
- Any suggested mitigations

### PGP Encryption

A PGP public key for encrypted email submissions will be published here and uploaded to
keys.openpgp.org once available. See issue
[#743](https://github.com/LucaDominici/arbiter/issues/743) for tracking.

## Plugin Trust Model

arbiter loads third-party plugins at runtime. The plugin isolation mechanism is **crash containment, not a security sandbox**.

- Plugin code runs in a Node.js `worker_threads.Worker` with memory limits (`maxOldGenerationSizeMb: 256`) and an empty environment (`env: {}`). Plugins cannot read `process.env` from the host unless the allowlist mechanism is implemented (deferred to a future issue).
- **What isolation prevents:** plugin hangs (timeout), OOM crashes, uncaught exceptions from propagating to the host process. Only `generate()` and `detect()` invocations are isolated — module-level code that runs during `require()`/`import()` of the plugin still executes in the main process (for shape validation).
- **What isolation does NOT prevent:** during shape validation, module-level code runs in the host process. A plugin that calls `process.exit()` or spins at module load time will still affect the host. Plugins can also still access `fs`, `net`, and `child_process` inside worker-isolated calls.
- **Trust boundary:** only install plugins from authors you trust, the same as any `npm` dependency.
- Plugins must declare `apiVersion: '1'` and export `name`, `templateRoot`, and `generate()`. Shape is validated before the worker is spawned.

This model is documented here per issue #620.

## Scope

This policy applies to the `arbiter` codebase (all files in this repository).

**In scope:**

- Source code under `src/`
- Generated templates under `src/templates/`
- CLI commands and build scripts
- Published npm package artifacts

**Out of scope:**

- Vulnerabilities in upstream dependencies (report to the upstream project)
- Security issues in code generated by arbiter in target projects (report to those
  project maintainers)

## Response Timeline and Severity Matrix

| Severity        | Examples                                                | Acknowledgment | Initial Assessment | Target Patch Window |
| --------------- | ------------------------------------------------------- | -------------- | ------------------ | ------------------- |
| **P0 Critical** | RCE, arbitrary code execution, supply-chain injection   | 24 hours       | 48 hours           | 24–48 hours         |
| **P1 High**     | Privilege escalation, credential leak, auth bypass      | 48 hours       | 7 days             | 7 days              |
| **P2 Medium**   | Information disclosure, path traversal (limited impact) | 48 hours       | 7 days             | 30 days             |
| **P3 Low**      | Minor info leaks, best-practice deviations              | 7 days         | 14 days            | 90 days             |

**Coordinated disclosure default:** 90 days from initial report, per industry standard.
Extensions may be granted if a fix is actively in progress.

---

## Process

1. Maintainer acknowledges receipt within the timeline above
2. Maintainer assesses severity and assigns a P-level
3. Fix is developed in a private branch or fork
4. Coordinated disclosure date is agreed with the reporter
5. Patch is released; a GitHub Security Advisory is published simultaneously
6. Reporter is credited in the advisory (unless anonymity is requested)
