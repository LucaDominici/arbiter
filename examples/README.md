# arbiter examples

This directory has two kinds of content, and they are deliberately not the same thing:

- **Generated living examples** (`ts-library/`, `python-library/`, `go-library/`) — real,
  committed output of `arbiter init`, regenerated by CI. If arbiter's generator changes
  what it produces, these directories drift from what's committed and the check goes red.
  Nothing here is hand-edited.
- **Hand-written walkthroughs** (`*.md`) — prose explaining the _why_ and _how_, covering
  archetypes and stacks the generated set doesn't (frontend-spa, backend-web-db, cli,
  data-pipeline). These are maintained by hand and can go stale between reviews; they are
  not verified by CI the way the generated examples are.

## Generated living examples (#1840 F4)

| Directory                              | Stack      | Archetype | Regenerated from                                   |
| -------------------------------------- | ---------- | --------- | -------------------------------------------------- |
| [`ts-library/`](./ts-library/)         | TypeScript | `library` | `__tests__/fixtures/real-projects/ts-library/`     |
| [`python-library/`](./python-library/) | Python     | `library` | `__tests__/fixtures/real-projects/python-library/` |
| [`go-library/`](./go-library/)         | Go         | `library` | `__tests__/fixtures/real-projects/go-library/`     |

These are the three README "Supported" stacks (TypeScript, Python, Go — see [Stack
support](../README.md#stack-support)) on the `library` archetype: the one archetype the
[Generator Matrix workflow](../.github/workflows/generator-matrix.yml)'s DEEP cells
actually exercise for all three today (the TypeScript cell always runs against
`ts-library`; the Python/Go cells match every `tier: functional` fixture for that
language, which currently includes `<lang>-library`). Tying the generated showcase to
that common cell keeps "regenerated by the matrix, drift = red" an honest claim instead
of a superset of what actually runs.

Each directory is the literal result of:

```bash
node dist/cli.js init --yes --tools claude --level L1 --no-verify --no-evidence \
  --language <typescript|python|go> --archetype library
```

run against a fresh copy of the matching fixture (minus `manifest.json`, which is
arbiter's own test-harness bookkeeping, not part of a real starter project).

**Regenerate / check for drift:**

```bash
npm run build
npm run examples:regenerate   # overwrite examples/<name>/ with today's generator output
npm run examples:check        # regenerate to a tmpdir and diff — exits 1 on any divergence
```

`node scripts/regenerate-examples.mjs --check` is what CI runs (see
`.github/workflows/generator-matrix.yml`) — one cell per stack, right after that stack's
existing DEEP functional test, using the toolchain the matrix already sets up. A generator
regression that changes rendered output shows up here as drift, not just as a passing/
failing test.

**Try one yourself:**

```bash
cp -r examples/ts-library /tmp/try-ts-library && cd /tmp/try-ts-library
npm install                       # devDependencies arbiter added aren't locked in the
                                   # committed package-lock.json — see note below
node scripts/check-all.mjs L1
```

Note on the committed `package-lock.json` in `ts-library/`: it is copied byte-for-byte
from the fixture (already regenerated under the pinned `npm@10.9.8`, #1861) and is NOT
re-locked after `arbiter init` adds devDependencies — re-locking during regeneration would
make "drift = red" sensitive to upstream dependency churn unrelated to arbiter's own
generator, which is not the signal this check exists to catch. Run `npm install` (not
`npm ci`) when trying the example locally, exactly as the [real-project fixture
dog-fooding instructions](../docs/internal/DEVELOPMENT/REAL-PROJECT-TESTING.md#dog-fooding-locally)
already recommend for TypeScript fixtures generally.

## Naming convention

Each example follows `<language>-<archetype>` to mirror the language/archetype axes used
by `src/compatibility/cross-language-matrix.json`. The hand-written walkthroughs are
markdown documents; their underlying starter projects live in
`__tests__/fixtures/real-projects/` so they double as the reference test fixtures
(INV-32) — the same fixtures the generated living examples above stage from.

## What each walkthrough covers

1. The starter project layout before `arbiter init` runs.
2. The exact `arbiter init` invocation (flags, governance level, AI tool selection).
3. The full list of files arbiter generates, grouped by purpose.
4. How to run the generated gate (`scripts/check-all.mjs`) at both L1 and L2.
5. A small, deliberate edit that triggers the enforcement chain so you can see hooks fire.

## Codespaces starter

[`examples/arbiter-starter/`](./arbiter-starter/) contains the minimal TypeScript skeleton used by the "Open in GitHub Codespaces" flow. It represents the project state _before_ `arbiter init` runs and is the fixture behind the `.devcontainer/` config in the repo root.

## Plugin examples

The plugin SDK exemplars live under `examples/plugins/` and `examples/plugin-spring-boot/`. They demonstrate the minimal `@arbiter/cli/plugin` contract per ADR-031.
